# 🍕 SQL1: Indexes and Query Optimization (Day 05)

## 📌 О проекте
Углубленное изучение механизмов индексирования в PostgreSQL для оптимизации производительности запросов. Проект охватывает создание различных типов B-Tree индексов (простые, функциональные, многоколоночные, уникальные и частичные), анализ планов выполнения запросов через `EXPLAIN ANALYZE`, достижение `Index Only Scan` и подбор покрывающих индексов (covering indexes) для ускорения сложных запросов с оконными функциями и `JOIN`.

Решения разбиты по директориям в соответствии с номерами заданий. В каждой папке находится один SQL-скрипт:

- 📁 **`src/ex01/`** → 📄 `day05_ex01.sql` (Доказательство использования индексов через `EXPLAIN ANALYZE` и отключение `seqscan`)

- 📁 **`src/ex03/`** → 📄 `day05_ex03.sql` (Многоколоночный индекс для достижения `Index Only Scan`)
- 📁 **`src/ex04/`** → 📄 `day05_ex04.sql` (Составной уникальный индекс для гарантии уникальности меню)

## ⚙️ Детальное описание выполненных задач

- **Part 1. Базовое индексирование и анализ планов (Tasks 00-01):**  
  Создал простые B-Tree индексы для всех внешних ключей в базе данных, соблюдая строгий нейминг (`idx_{table}_{column}`). Для доказательства их использования планировщиком запросов написал `SELECT` с `JOIN` и применил `EXPLAIN ANALYZE`. Чтобы заставить оптимизатор использовать созданные индексы на малом объеме данных, принудительно отключил последовательное сканирование (`SET enable_seqscan = OFF`).

- **Part 2. Функциональные и многоколоночные индексы (Tasks 02-03):**  
  Реализовал функциональный индекс `idx_person_name` для быстрого поиска без учета регистра (`UPPER(name)`). В задании 03 спроектировал многоколоночный индекс `idx_person_order_multi`, который полностью покрывает условия фильтрации и возвращаемые поля запроса. Это позволило планировщику выбрать наиболее эффективный метод доступа — `Index Only Scan` (чтение только из дерева индекса без обращения к heap-таблице).

- **Part 3. Обеспечение целостности и частичные индексы (Tasks 04-05):**  
  Создал составной уникальный индекс `idx_menu_unique` для предотвращения дубликатов названий пицц в рамках одной пиццерии на уровне БД. В задании 05 реализовал частичный (partial) уникальный индекс `idx_person_order_order_date`, который обеспечивает уникальность заказов конкретного меню конкретным клиентом только для определенной даты ('2022-01-01'). Это существенно экономит дисковое пространство и ускоряет целевые запросы.

- **Part 4. Глубокая оптимизация и покрывающие индексы (Task 06):**  
  Провел технический анализ сложного запроса с `INNER JOIN` и оконной функцией (`OVER PARTITION BY`). Методом итеративного подбора создал оптимальный покрывающий индекс `idx_1`, который изменил план выполнения (переход от `Merge Join` к `Nested Loop` с `Index Scan`) и значительно снизил фактическое время выполнения (`Execution Time`), что было зафиксировано и доказано через сравнение выводов `EXPLAIN ANALYZE` до и после создания индекса.

## 🚀 Как проверить

1. **Подготовка:** Убедись, что у тебя развернута СУБД PostgreSQL, применен скрипт `model.sql`, и сохранены все изменения данных из предыдущих дней (Day 03 и Day 04).
2. **Запуск:** Перейди в директорию `src/exXX` и запусти файл `day05_exXX.sql` через терминал (`psql -d your_db -f day05_exXX.sql`) или графический клиент.
3. **Валидация:** Для каждого задания проверяйте вывод `EXPLAIN ANALYZE`. Убедитесь, что в плане выполнения присутствуют узлы `Index Scan` или `Index Only Scan` (там, где это требуется). Для задания 06 сравните метрики `Planning Time` и `Execution Time` до и после создания индекса `idx_1`.
